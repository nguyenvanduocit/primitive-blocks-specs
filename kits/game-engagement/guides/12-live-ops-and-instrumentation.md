# Live Ops and Instrumentation

A live game is run through numbers and levers: events that say what players did, metrics defined once, configuration the server controls, experiments that change one thing, a calendar with owners, and an engineering floor that keeps currency and progress honest. This guide owns the event envelope and the core event taxonomy that every block in the kit uses, plus the operating discipline around them. Acquisition measurement is in `05-marketing-and-launch.md`, economy design in `03-economy-and-offers.md`, and the privacy and minors floor in `06-design-ethics-and-compliance.md`.

Evidence: Apple, Google, Firebase, FTC, EU and ICO pages read on 2026-10-27, plus Amplitude, devtodev, Microsoft's experimentation team, OWASP and design essays, and the event sections of the eleven blocks in this repository (HIGH for what they define), named inline with HIGH, MEDIUM or LOW. Platform facts come from the current official pages. Metric and experiment practice comes from vendors and practitioners, and no source gives game-specific thresholds (see Gaps).

## Decision rule

1. **Fix one envelope for every event.** Required fields: `event_name`, `account_id`, `session_id`, `server_ts`, `client_ts`, `app_version`, `platform`, plus `event_id` (a client-generated unique id, so retried sends are de-duplicated) and `schema_version` (an integer per event name). Envelope fields sit at the top level and event properties in one flat `properties` object, so a property can never overwrite an envelope field: `live_event_joined` carries the live event's id as the property `event_id`, a different field from the envelope's `event_id`. `server_ts` is stamped on receipt and is the only clock a metric or cohort uses; `client_ts` measures device drift and orders events inside a session, in line with the time contract (the server clock is the authority). The envelope is this kit's design (MEDIUM).
    - A server event written outside a player request (ingestion, settlement, sweeps) has no session: `session_id` is null, and so is `client_ts` when no client sent the event, and an omitted field reads as null (`blocks/engagement/season-pass/README.md:844` states the first; `blocks/engagement/event-calendar/frontend.md:303` omits both).
    - A few events have no account, so `account_id` is absent: `guest_purged` (the account is gone) and `guest_create_throttled` (none exists yet); a client event fired while identity is pending carries an empty `account_id` (`blocks/auth/guest-account/README.md:981-984`). Ingestion keeps these events and never drops one for a missing `account_id`.
    - A session starts when the app reaches the foreground with no live session and ends after an inactivity timeout you choose and write down; Google Analytics defaults to half an hour ([Google Analytics Help](https://support.google.com/analytics/answer/9191807), HIGH that this is its default, a vendor setting and not a standard). `engagement.objectives` closes a session window after `SESSION_IDLE_TIMEOUT_SECONDS`, default 1800 (`blocks/engagement/objectives/README.md:652`); give the analytics timeout the same value so the two agree.
2. **Name events as facts and cap their shape.** Use `<object>_<verb>` in snake_case, one event per fact, flat properties, enumerated values, no free text. A block's events lead with its own object (`queue_`, `item_`, `season_pass_`, `live_event_`, `push_`), and the index below names one owner per event, so check it before adding a name. Internal domain events on the server bus (`objective.completed`, `event_published`, `subscription_state_changed`) feed other blocks and are not analytics events. Keep names within 40 characters and each event within 25 parameters, and plan for at most 500 distinctly named events per app user, so a Google Analytics app stream can ingest them ([Google Analytics Help](https://support.google.com/analytics/answer/9267744), HIGH). Adding a property is safe. Changing a property's meaning or type, or the moment an event fires, takes a new `schema_version` and a release that writes both versions (kit rule, MEDIUM).
3. **Keep personal data and secrets out of events, and treat the stream as personal data anyway.** Never put an email, name, phone number, precise location, IP address, advertising id, player-typed text, auth token, store receipt or API key in an event. `account_id` is a pseudonym, and pseudonymised data that can be attributed to a person with additional information is information on an identifiable person ([GDPR Recital 26](https://gdpr-info.eu/recitals/no-26/), HIGH), so the event store follows rule 24.
4. **Write money, claim and accepted-progress events on the server, in the same transaction as the state change.** The client writes what only it sees: session, screens, tutorial steps, ad impressions, push opens, uncaught errors. Events that ask `messaging.push-reengagement` to notify a player carry their own fields (Hand-off events below). `currency_grant` and `currency_spend` carry the ledger `entry_id` from `billing.virtual-currency`, so a daily job that compares event sums with ledger sums per currency and `reason` finds dropped or duplicated events (kit design, MEDIUM). Rewarded ads reward through the ad network's server-side verification where it exists: AdMob's server-side verification "provides an extra layer of protection against spoofing of client-side callbacks to reward users" ([Google](https://developers.google.com/admob/android/rewarded-video-ssv), HIGH).
5. **Define every metric once, with its denominator** (table below), and print the definition on the dashboard. Classic and rolling retention differ by large margins: Amplitude's example reads day 1 as 43% classic and 59% unbounded, and a studio that quoted "day 1 above 55%, day 7 above 25%" had quoted unbounded figures ([Amplitude](https://amplitude.com/blog/n-day-retention-for-mobile-games), MEDIUM, vendor). Report classic as the headline for D1, D7 and D30, with rolling beside it for games players open less than daily.
6. **Build cohort views, not averages.** Retention curves (both definitions) by install day, `app_version`, platform, country and acquisition channel; D1 split by `tutorial_step` completion; cumulative revenue per install with a payback marker; payer versus non-payer retention; time to first `purchase_verified`; participants versus non-participants in each live event (self-selected, so correlational, as in guide 03 rule 5). A day-N figure is published only after day N has passed for every install in the cohort.
7. **Benchmarks are scale only; targets come from the soft launch** (guide 01 rule 6, guide 05 rule 3). No benchmark summary read here says whether its retention is classic or rolling, or counted by calendar date or by a window, so none can be compared with your cohorts. A day-1 value near 30% read to within three points at 95% confidence needs about 900 installs (n = 1.96² · p(1 − p) / 0.03², kit arithmetic); a smaller soft-launch cohort gives a range, not a gate.
8. **Make the ledger the audit source and watch five views.** `billing.virtual-currency` is the only writer of balances, and its registry `currency_flows` names every faucet and sink by direction and `reason` (`blocks/billing/virtual-currency/README.md:843`); a write whose reason has no enabled row of the right direction is rejected (INV-7, `blocks/billing/virtual-currency/README.md:1058`), so a reason missing from the registry is a finding, and `ledger_rejected` events count the attempts. (a) Faucets and sinks by `reason`, per currency per day, with net flow, which Raph Koster named as the main health indicator of a live MMO economy ([Koster, 2004](https://www.raphkoster.com/games/essays/astromech-stats-economy-stats/), MEDIUM, old and another genre). (b) Balance percentiles and the top-1% share per currency; the ledger's `holders(currency)` read pages accounts with a balance above zero by an `account_id` cursor, at most `HOLDERS_MAX_LIMIT` (default 500) per page, read-only and in process (`blocks/billing/virtual-currency/README.md:831`, `:980`), so a nightly job can page it to build the view (kit use, MEDIUM). (c) Accounts whose balance jumps beyond their history, which Koster used to spot duping and cheating (MEDIUM). (d) The offer funnel `offer_shown` to `purchase_verified` by `offer_id` and placement. (e) Time to the first moment a player cannot afford what they want (kit idea, LOW). Alarm on drift from your own trailing same-weekday baseline. The ratios that circulate (a faucet-to-sink band, a Gini cut-off) trace to single blogs and are not used (LOW). Inflation means faucets exceed sinks (guide 03 rule 3).
9. **Server-control data, never code or secrets.** Server-controlled: reward amounts and tables, timer lengths (the server evaluates them; the client shows `ends_at`), live-event definitions (`engagement.event-calendar`), which store product fills which slot and in what order, ad-placement switches, copy keys, experiment arms, `min_supported_version`, and one kill switch per feature. Not remote: secrets, because "Don't store confidential data in Remote Config parameter keys or values" and any value available to the app is readable by players ([Firebase](https://firebase.google.com/docs/remote-config/parameters), HIGH); the price a player pays, which the store owns, so display `Product.displayPrice` ([Apple](https://developer.apple.com/documentation/storekit/product/displayprice), HIGH) or `getFormattedPrice()` ([Android](https://developer.android.com/reference/com/android/billingclient/api/ProductDetails.OneTimePurchaseOfferDetails), HIGH); any client-side decision on balance or entitlement; and code. Apple 2.5.2 bars downloading or executing code that introduces or changes features, so flags switch features already in the binary, and 2.5.19 bars hidden, dormant or undocumented features, so describe each flag-gated feature in the review notes ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), HIGH for the text, MEDIUM for the reading).
10. **Ship safe defaults, ramp by percentage, roll back by version.** Compile in defaults: "Don't rely on network connectivity to obtain Remote Config values. Do set in-app default parameter values" ([Firebase](https://firebase.google.com/docs/remote-config/loading), HIGH). The server rereads config when it grants, so a stale client copy never sets value. Ramp a change by a stable hash of `account_id`, pausing at each step to read guardrails (Firebase supports random percentage rollouts, HIGH). Rolling back is publishing the previous version; Firebase keeps up to 300 versions per template type and a rollback creates a new version with the old content ([Firebase](https://firebase.google.com/docs/remote-config/templates), HIGH). Store halts do not undo installed builds: on Google Play, users already on a staged version "remain on that version" ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/6346149), HIGH), which is why kill switches live on the server. Log author, reason and version for every change.
11. **One change, one primary metric, named guardrails, written before launch.** Guardrails are metrics for "aspects of the product that we don't want to degrade but won't necessarily improve" ([Microsoft Research](https://www.microsoft.com/en-us/research/articles/patterns-of-trustworthy-experimentation-during-experiment-stage/), HIGH). Interstitials added to a rewarded-only game raised revenue 17% and ARPDAU 18% and cut D7 retention 2.3% (guide 03 rule 5), which is why D7 is a default guardrail, with crash and ANR rate, sessions per DAU, refund rate and support contacts. Assign arms on the server by hashing `account_id` with the experiment id, keep them sticky, log `experiment_exposed`, and run one live experiment per surface.
12. **Check validity, then read.** A sample ratio mismatch (the observed split differs from the configured one, flagged by a chi-square test at p < 0.0005) invalidates the result until the cause is found ([Microsoft Research](https://www.microsoft.com/en-us/research/articles/diagnosing-sample-ratio-mismatch-in-a-b-testing/), HIGH). Run to the planned end ("we recommend running the test until the end of its pre-determined duration"); a fast decline of the effect across date segments signals a novelty effect (Microsoft, HIGH, web products; Microsoft's typical test lasts a week). Read new-player tests on D1, then judge D7 (guide 01 Gaps, LOW). Firebase A/B Testing names a leader only after two weeks for Remote Config tests ([Firebase](https://firebase.google.com/docs/ab-testing/abtest-config), HIGH, tool behavior). Detecting day-1 retention moving from 30% to 32% at 5% significance and 80% power takes about 8,400 new players per arm (n = 2 · (1.96 + 0.84)² · p̄(1 − p̄) / δ² with p̄ = 0.31 and δ = 0.02, kit arithmetic), so a soft launch tests only large effects.
13. **Do not test on players who cannot protect themselves, and test only what you would ship.** No arm raises price pressure, scarcity, spend prompts or odds opacity for minors or accounts of unknown age, and no arm is targeted by vulnerability signals such as spend spikes, long late-night sessions or repeated losses (kit rule). Regulators judge by vulnerability: the EU Unfair Commercial Practices Directive assesses a practice from the standpoint of a clearly identifiable vulnerable group (Art. 5(3), [EUR-Lex](https://eur-lex.europa.eu/eli/dir/2005/29/2022-05-28/eng), MEDIUM, the text was seen only through a search summary of a legislation.gov.uk copy), the EU consumer authorities' principles ask that game design respect vulnerabilities, especially those of children ([Reed Smith summary](https://www.reedsmith.com/en/perspectives/2025/03/qas-on-the-eu-consumer-protection-authorities-joint-guidance-paper), MEDIUM, soft law), and the UK Age Appropriate Design Code has standards on profiling, nudge techniques and detrimental use of data ([ICO](https://www.ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/childrens-information/childrens-code-guidance-and-resources/age-appropriate-design-a-code-of-practice-for-online-services/), HIGH that they exist; their text was not retrieved). An arm that changes odds on a purchasable random reward shows the odds it applies (Apple 3.1.1, [App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), HIGH). Published examples: Supercell's chest experiment covered King Tower levels 1 to 9 only and held total reward value constant, and the page names no groups, metrics or results ([Supercell](https://supercell.com/en/games/clashroyale/blog/news/chest-experiment-king-tower-levels-1-9), HIGH for the page); Duolingo's streak test is in guide 02.
14. **Run one calendar with named owners, and QA with a test clock.** `engagement.event-calendar` holds definitions; each entry has an owner, a second reviewer and a state (draft, in QA, scheduled, live, closed). Add layers in the order of guide 02 rule 1, as fast as the team can ship to the calendar. QA uses a server-side clock offset on the account, available only to allowlisted tester accounts and enforced on the server, never a client setting; test accounts are flagged and excluded from every metric and ledger report (kit design, no source). Each closed event gets a review: participation, reward value granted by `reason`, guardrails.
15. **Handle an incident in five steps.** Stop (kill switch, pause the event). Scope from the ledger by `reason` and `source_ref`, not from event counts. Correct through the ledger contract with compensating entries whose reason names the incident, never by editing or deleting entries. Tell players what happened and what they get, in the in-game inbox or news slot, without blame. Hold a blameless postmortem whenever a trigger set beforehand fires, such as data loss, a rollback or a manual intervention ([Google SRE book](https://sre.google/sre-book/postmortem-culture/), HIGH). For over-granted rewards already spent, the kit default is to honor what was spent and remove only the unspent remainder (kit recommendation, LOW, no source).
16. **The server is the authority.** Currency, progress, timers, rewards, entitlements and purchase verification live on the server and the client sends intents. Apple: "You can't rely on your app's logic to perform security checks on itself because a compromised app can falsify the results" ([Apple](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity), HIGH). Take `account_id` from the session, never the request body; validate type, range, ownership and plausibility (a level cannot finish faster than its minimum possible time); make every grant idempotent through the ledger key. Rate-limit per account and address, tighter on claim, purchase and score endpoints: OWASP says "Rate limiting should be fine tuned based on the business needs" and lists sensitive business flows as their own risk ([OWASP API4](https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/), [API6](https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/), HIGH). Answer with 429 and an optional Retry-After header ([RFC 6585](https://www.rfc-editor.org/rfc/rfc6585#section-4), HIGH); clients retry with exponential backoff and jitter, "a standard approach for remote clients" ([AWS](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/), HIGH).
17. **Use platform integrity as a risk signal, not a verdict.**
    - Apple App Attest: one key per account per device, a server challenge of at least sixteen bytes, the server verifies the attestation and stores the public key per account and device, assertion counters must increase, and a server-to-server call returns the number of attested keys for a device over the past thirty days, which exposes one compromised device serving many app instances. Keys do not survive reinstall or restore, unsupported devices bypass gracefully, and apps with millions of daily users ramp gradually ([establishing](https://developer.apple.com/documentation/devicecheck/establishing-your-app-s-integrity), [validating](https://developer.apple.com/documentation/devicecheck/validating-apps-that-connect-to-your-server), [fraud risk](https://developer.apple.com/documentation/devicecheck/assessing-fraud-risk), HIGH).
    - Google Play Integrity: standard requests return app, device and account verdicts decrypted on Google's servers, bind to the request through `requestHash`, block token replay automatically, default to 10,000 requests per day per Cloud project, and Google advises tiered backend responses ([standard](https://developer.android.com/google/play/integrity/standard), [setup](https://developer.android.com/google/play/integrity/setup), [overview](https://developer.android.com/google/play/integrity/overview), HIGH).
    - Kit policy: log the verdict with every high-value request (claim, purchase, ranked score), respond by tier (allow, challenge, restrict), and never hard-block on a missing verdict, which legitimate players on unsupported devices produce. Other signals: counter regressions, one receipt or key across accounts, impossible progress speed, balance jumps. No source gives thresholds (Gaps).
18. **Hold stability targets below the stores' lines.** Google Play bad-behaviour thresholds: user-perceived crash rate 1.09% of daily active users overall and 8% on one phone model; user-perceived ANR rate 0.47% overall and 8% per phone model; excessive partial wake locks 5%; assessed over the last twenty-eight days; exceeding one may reduce visibility or add a listing warning, and memory, bitmap and code-optimization thresholds may affect visibility from February 2027 ([Android vitals](https://developer.android.com/topic/performance/vitals), HIGH). Apple publishes no store-visibility threshold that this guide found. Xcode Organizer shows goals from similar apps and from your own history ([Apple](https://developer.apple.com/documentation/xcode/analyzing-the-performance-of-your-shipping-app), HIGH), hang reporting starts at 250 ms of main-thread unresponsiveness ([Apple](https://developer.apple.com/documentation/xcode/understanding-hangs-in-your-app), HIGH), and MetricKit delivers daily on-device reports ([Apple](https://developer.apple.com/documentation/metrickit), HIGH). Alarm on your own baseline well under Google's lines, per `app_version` and device model. Release in stages and halt on a crash or ANR spike: Play staged rollouts, and Apple's phased release (1%, 2%, 5%, 10%, 20%, 50%, then 100% over a week, pausable; [App Store Connect Help](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases/), HIGH).
19. **Plan for offline and flaky networks.** Android's offline-first guidance: perform a critical subset of functionality without internet, let local data lag the network source, and sync when connectivity returns ([Android Developers](https://developer.android.com/topic/architecture/data-layer/offline-first), HIGH). For a game: anything that moves currency, reward or purchase state is online-only or queued as an intent with its idempotency key, the UI shows pending until the server answers (no optimistic grant the server may reject), progress syncs through `data.progress-sync`, timers display from `server_now` and `ends_at`, and analytics events queue on the device with `event_id`, flush in batches and drop the oldest beyond a cap (kit design, MEDIUM).
20. **Version the contract and force updates through the server.** The server holds `min_supported_version` and `recommended_version` per platform, checked at start and resume: below the minimum, a blocking screen with the store link; below the recommended, a dismissible nudge. Keep the API additive across the two newest versions (kit rule). Google Play offers flexible and immediate in-app update flows, `inAppUpdatePriority` from 0 to 5 per release and `clientVersionStalenessDays()` ([Android Developers](https://developer.android.com/guide/playcore/in-app-updates/kotlin-java), HIGH). No Apple in-app update API appears in the documentation read, so the server check serves iOS (LOW, an absence).
21. **Localize and make accessible from the first build.** Send `copy_key` plus parameters, not rendered strings; choose plural forms by CLDR category (`zero`, `one`, `two`, `few`, `many`, `other`; `other` is required and the names are mnemonics; [Unicode CLDR](https://cldr.unicode.org/index/cldr-spec/plural-rules), HIGH); show prices from store strings. Accessibility floor: iOS default control size 44 by 44 points (minimum 28 by 28), text enlargeable by at least 200 percent, contrast 4.5:1 for text up to 17 points and 3:1 for 18 points and above or bold ([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/accessibility), HIGH); WCAG 2.2 criterion 2.5.8 asks for 24 by 24 CSS pixels at level AA, which applies to a web-tech client ([W3C](https://www.w3.org/TR/WCAG22/), HIGH); the Game Accessibility Guidelines basic tier adds large well-spaced controls, a readable default font, no information by colour alone and subtitles for important speech ([GAG](https://gameaccessibilityguidelines.com/basic/), MEDIUM, community guideline). Timed reward windows stay reachable for slower players (kit rule).
22. **Declare what you collect.** Apple counts analytics-SDK collection as yours and lists Analytics as a purpose ([App Privacy Details](https://developer.apple.com/app-store/app-privacy-details/), HIGH); Google's Data safety form covers SDKs and the analytics purpose and "must remain accurate and complete at all times" ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/10787469), HIGH).
23. **Apply ATT, EEA and UK consent, and the children's floor.**
    - ATT is needed to link your data with other companies' data for targeted advertising or measurement, or to share it with data brokers; hashed email is no substitute after a denial ([Apple](https://developer.apple.com/app-store/user-privacy-and-data-use/), HIGH). First-party events on your own server keyed by `account_id` fall outside that definition (kit inference from it, MEDIUM); an SDK or attribution partner that joins them with other companies' data falls inside (guide 05 rule 7).
    - EEA: the EDPB says collecting unique identifiers in websites or mobile applications is a "gaining of access" under ePrivacy Article 5(3) ([EDPB Guidelines 2/2023, para. 63](https://edpb.europa.eu/system/files/2024-10/edpb_guidelines_202302_technical_scope_art_53_eprivacydirective_v2_en_0.pdf), HIGH), so start non-essential analytics and advertising SDKs only after consent; whether an operational event is strictly necessary is a legal question. UK: the PECR statistics exception needs clear information, a free and simple objection and a sole statistical purpose ([ICO](https://ico.org.uk/for-organisations/direct-marketing-and-privacy-and-electronic-communications/guidance-on-the-use-of-storage-and-access-technologies/what-are-the-exceptions/), MEDIUM; the page does not address app SDKs).
    - Children: GDPR Article 8 sets consent at 16, which Member States may lower to no less than 13 ([GDPR](https://gdpr-info.eu/art-8-gdpr/), HIGH). The amended COPPA Rule took effect on 2025-06-23, with compliance due 2026-04-22 for most provisions, and requires a written data retention policy ([Federal Register](https://www.govinfo.gov/content/pkg/FR-2025-04-22/pdf/2025-05904.pdf), HIGH) and separate verifiable parental consent before disclosure to third parties ([FTC](https://www.ftc.gov/news-events/news/press-releases/2025/01/ftc-finalizes-changes-childrens-privacy-rule-limiting-companies-ability-monetize-kids-data), HIGH). Apple 1.3 and 5.1.4 bar third-party analytics and advertising in the Kids Category and in apps intended primarily for kids ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), HIGH). Google Play Families lets child-directed apps use only approved SDKs and bars sending the advertising id ([Google](https://support.google.com/googleplay/android-developer/answer/9893335), HIGH).
    - Kit rule: a game likely to be played by children uses first-party analytics only, no advertising id, no monetization experiments and no personalized offers (guide 06, interview 4).
24. **Set retention windows and erase by design.** GDPR Article 5 requires data "limited to what is necessary" and kept in identifiable form only for as long as the purposes need ([GDPR](https://gdpr-info.eu/art-5-gdpr/), HIGH). Give each table a window (raw events, ledger, purchase records, crash reports) and keep aggregates free of `account_id`. Apple 5.1.1(v) requires in-app account deletion when the app supports account creation ([App Review Guidelines](https://developer.apple.com/app-store/review/guidelines/), HIGH); events follow `compliance.account-deletion`: delete them or de-identify them by dropping `account_id`. Retention of payment records is a legal question for the operator (`blocks/compliance/account-deletion/README.md`, HIGH, in this repository).

## Core events

| Event | Fires when | Properties beyond the envelope | Written by |
|---|---|---|---|
| `session_start` | App reaches the foreground with no live session | `session_number`, `entry` (cold, resume, push, link), `config_version` | client, game |
| `session_end` | Inactivity timeout or close; the OS often kills the app first, so derive the end from the last event | `duration_ms` | client, game, derived |
| `tutorial_step` | A tutorial step is shown, completed or skipped | `step_id`, `step_index`, `outcome` | client, game |
| `level_start` | A level begins | `level_id`, `attempt_number` | client, game |
| `level_complete` | The server accepts a completion; also the default qualifying-play action code of `engagement.daily-streak` (`blocks/engagement/daily-streak/README.md:604`) | `level_id`, `attempt_number`, `duration_ms`, `score` | server, game |
| `level_fail` | A round ends in failure | `level_id`, `attempt_number`, `duration_ms`, `fail_reason` | client, game |
| `currency_grant` | A `grant` or `reinstatement` is applied (`reason` shows which) | `currency`, `amount`, `balance_after`, `reason`, `source_ref`, `entry_id` | server, `billing.virtual-currency` |
| `currency_spend` | A `spend` or `clawback` is applied | same as `currency_grant` | server, `billing.virtual-currency` |
| `purchase_verified` | A purchase first becomes verified, once per `store_transaction_id` | `product_code`, `offer_id`, `currency_code`, `price_micros`, `price_currency`, `price_source`, `platform`, `environment`, `first_purchase_bonus_applied`, `latency_ms` | server, `billing.virtual-currency` |
| `purchase_refunded` | A store refund is applied | `product_code`, `refund_reason`, `platform`, `clawed_total`, `shortfall_total` | server, `billing.virtual-currency` |
| `offer_shown` | An offer card is displayed, once per card per view | `offer_id`, `placement` (`shop`, `starter_banner`, `insufficient_balance`) | client, `billing.virtual-currency` |
| `ad_shown` | An ad impression is displayed | `placement`, `ad_format`, `network` | client, game |
| `ad_rewarded` | A rewarded ad's reward is granted | `placement`, `reward_ref` | server, game |
| `objective_progress` | An instance's progress changed in a request, one event per instance per request | `objective_id`, `progress`, `target`, `scope` | server, `engagement.objectives` |
| `objective_claimed` | A claim succeeds | `objective_id`, `entry_id` (first reward line), `scope`, `claim_source`, `reward_lines` | server, `engagement.objectives` |
| `live_event_joined` | An account first takes part in a live event | `event_id` (the live event's id), `cadence_layer`, `join_mode`, `state` | server, `engagement.event-calendar` |
| `experiment_exposed` | An account first sees an experiment arm | `experiment_id`, `arm` | server, game |
| `push_delivered` | A delivery signal arrives: `source` is `client` when app code ran on delivery, `provider` when the provider reported it | `category`, `provider`, `source` | server, `messaging.push-reengagement` |
| `push_opened` | The player taps a notification | `lane`, `category`, `route`, `cold_start`, `send_id` or `local_key` | client, `messaging.push-reengagement` |
| `error` | An uncaught client error reaches the global handler | `error_code`, `surface`, `fatal` | client, game |

Rows written by `game` have no block behind them; this guide defines them (no block emits `session_start`, `session_end`, `tutorial_step`, `level_start`, `level_fail`, `ad_shown`, `ad_rewarded` or `experiment_exposed`). Every other row carries the names and properties its block defines: `currency_grant` to `purchase_refunded` at `blocks/billing/virtual-currency/README.md:949-952`, `offer_shown` at `blocks/billing/virtual-currency/frontend.md:88`, `objective_progress` and `objective_claimed` at `blocks/engagement/objectives/backend.md:408` and `:410`, `live_event_joined` at `blocks/engagement/event-calendar/frontend.md:312`, `push_delivered` at `blocks/messaging/push-reengagement/README.md:829` and `push_opened` at `:817`. `error` is for uncaught client errors only: blocks keep their own named failures (`season_pass_error_shown`, `queue_error_shown`, `sign_in_failed`, `daily_reward_claim_failed`, `objective_claim_failed`, `live_event_claim_failed`, `push_route_failed`, `ledger_rejected`), and a handled failure never also fires `error`. On Android, FCM notification messages are shown by the SDK while the app is in the background, so only data messages run app code ([FCM message types](https://firebase.google.com/docs/cloud-messaging/customize-messages/set-message-type), HIGH), which is why `push_delivered` has two sources; `push_sent` (`blocks/messaging/push-reengagement/README.md:828`) counts sends. The event and property names are this kit's design where a row says `game` (MEDIUM).

## Hand-off events

Six blocks ask `messaging.push-reengagement` to notify a player by emitting one event on the shared bus; no emitter calls the push block or waits for it (`blocks/messaging/push-reengagement/README.md:736`). The event carries the envelope plus five fields (`blocks/messaging/push-reengagement/README.md:729-734`); `queue_item_ready` adds `ends_at` and `revision`:

| Field | Meaning |
|---|---|
| `subject_key` | Stable for one occurrence, so a later `armed` or `resolved` addresses the same notification |
| `state` | `armed` (schedule it, or move it) or `resolved` (cancel the pending one); `armed` by default |
| `fire_at` | Absolute server time to show it; the event's `ends_at` when it has one, else `server_ts` |
| `expires_at` | The notification is pointless after this instant; `fire_at` plus the category `ttl_seconds` by default |
| `params` | Flat template variables and route parameters; a template uses the variables it names |

| Event | Emitter | Lane | `subject_key` as the emitter defines it | Defined at |
|---|---|---|---|---|
| `streak_at_risk` | `engagement.daily-streak` | local | `streak:{day_key}` | `blocks/engagement/daily-streak/README.md:587`, `:592` |
| `energy_full` | `engagement.energy-lives` | local | `energy:{meter_code}:{cycle_started_at as epoch seconds}` | `blocks/engagement/energy-lives/README.md:687-692` |
| `queue_item_ready` | `engagement.timed-queues` | local | `queue-item:{item_id}` | `blocks/engagement/timed-queues/README.md:590` |
| `event_ending_soon` | `engagement.event-calendar` | remote | `event:{event_id}` | `blocks/engagement/event-calendar/README.md:734` |
| `objective_reward_ready` | `engagement.objectives` | remote | `objective:{objective_id}:{window_key}` | `blocks/engagement/objectives/README.md:632` |
| `subscription_trial_ending` | `billing.subscriptions` | remote | `trial:{term_id}:{reminder_seq}` | `blocks/billing/subscriptions/README.md:817-829` |

An emitter sends `armed` once per `subject_key`, sends it again with the same `subject_key` when `fire_at` or `expires_at` moves (a speed-up, an extension), and sends `resolved` with the same `subject_key` when the reason clears (a claim, a refill, a cancel). Delivery is at-least-once through a transactional outbox or equivalent, and the consumer upserts by (account, event, `subject_key`) (`blocks/engagement/energy-lives/README.md:694`). A local-lane event is also emitted by the client, which schedules the local notification from state it holds; the server ingest drops a local-lane event with reason `lane_mismatch` (`blocks/messaging/push-reengagement/README.md:736`). Dashboards count a hand-off event once per `subject_key`, not once per re-emission (kit rule), and measure reach from `push_sent`, `push_delivered` and `push_opened`, not from the hand-off.

## Metric definitions

| Metric | Definition | Note |
|---|---|---|
| Day-N retention, classic | Share of an install-day cohort with a session on calendar day N; day 0 is the install day | One reporting timezone; one app read day 1 as 43% by calendar date and 32% by twenty-four-hour windows ([Amplitude](https://amplitude.com/blog/n-day-retention-for-mobile-games), MEDIUM) |
| Day-N retention, rolling | Share with a session on day N or any later day | Never below classic; suits timed-build games and misleads in daily-use games ([devtodev](https://www.devtodev.com/resources/articles/main-metrics-rolling-retention), MEDIUM); Amplitude calls it "Return On or After" ([docs](https://amplitude.com/docs/analytics/charts/retention-analysis/retention-analysis-interpret), HIGH) |
| Sessions per user, session length | Sessions divided by users; total duration divided by session count | Depends on the timeout in rule 1 ([devtodev glossary](https://devtodev.com/resources/articles/game-analytics-metrics-glossary), MEDIUM) |
| DAU, MAU, stickiness | Unique active accounts per day and per month; stickiness is DAU divided by MAU | Define "active" as one session; devtodev gives DAU and MAU, and the ratio is this kit's reading (MEDIUM) |
| ARPDAU | Revenue on a day divided by that day's DAU | Declare gross or net of store fees; report ad and purchase revenue apart |
| Payer conversion | Cohort view: share with at least one `purchase_verified` by day N. Daily view: paying users divided by active users | The sources give "paying share = paying users / active users" and no single conversion formula (devtodev, MEDIUM) |
| ARPPU | Revenue from payers divided by payers over a stated period | A payer made at least one payment (devtodev, MEDIUM); state the period |
| LTV and payback | LTV is cumulative revenue per install by cohort day N; payback is the first day it reaches CPI (guide 05) | The ratio of long-window to day-7 revenue is unstable, so early ROAS predicts payback poorly ([Liftoff, 2020](https://liftoff.io/?p=27508), LOW, read through a search summary); label predicted LTV as predicted |

## Default path

1. Write the envelope, the event table, the block event index and the metric definitions into the project contract, and build one client wrapper that stamps `event_id`, `schema_version` and `session_id` and queues offline (rules 1 to 4).
2. Instrument tutorial steps, levels, the ledger, purchases, offers, ads and errors before the soft launch, then build the cohort views and the daily ledger reconciliation (rules 4 to 8).
3. Put the server-control list behind remote config with compiled defaults, per-feature kill switches and a version log (rules 9 and 10).
4. Add server validation, rate limits, integrity logging and the minimum-version gate before the first public build (rules 16 to 20).
5. Soft-launch, then write retention, payback and stability gates from the first cohorts; run a first experiment only once guardrails and the mismatch check exist (rules 7, 11, 12, 18).
6. Stand up the calendar, the test clock and the incident runbook before the first live event (rules 14 and 15).
7. Review privacy labels, consent, children handling, retention windows and deletion with counsel before each store submission (rules 22 to 24).

## Gaps

- No source gives game-specific numbers for economy alarms, anti-cheat cut-offs (attested keys per device, impossible-speed limits) or a healthy faucet-to-sink ratio; the figures in circulation trace to single blogs.
- No benchmark summary states whether its retention is classic or rolling, or counted by calendar date or window, so guide 01's public figures cannot be reconciled with your cohorts.
- Microsoft's experiment guidance comes from web products; no source gives how long a game experiment must run, or how long a novelty effect lasts in a game. The primary experiment papers (Kohavi and colleagues) were not read; only Microsoft's own summaries were.
- No controlled study covers live-ops process (calendar cadence, freeze rules, incident comms, compensation policy); those steps are kit design. Neither App Attest nor Play Integrity publishes detection rates.
- Apple's store-visibility thresholds for crashes and hangs, and an Apple in-app forced-update API, were not found.
- Legal items not settled: the UK Data (Use and Access) Act 2025 changes to PECR (read only through secondary sources), national ePrivacy practice for in-app analytics, US state laws on app-store age verification, age-signal APIs, and Vietnam's personal-data and data-localization rules. The EU consumer principles on virtual currencies are soft law (guide 06 covers the enforcement picture).
- The index lists what the eleven block files define on 2026-10-27; those files can change, and the guide does not track them.
- Not researched: event-pipeline and warehouse products, fraud-scoring vendors, and support tooling.

## Checklist

- [ ] The envelope, the event table and the metric definitions are in the project contract, and every block's events use them.
- [ ] Money, claim and accepted-progress events are written by the server, and a daily job reconciles them with the ledger.
- [ ] No personal data, secret or player-typed text is in any event.
- [ ] Envelope fields sit at the top level and properties in one flat object; server events outside a player request carry a null `session_id`, and events without an account omit `account_id` and are kept.
- [ ] Each hand-off event sends `armed` once per `subject_key`, re-arms when `fire_at` or `expires_at` moves, and sends `resolved` when the reason clears.
- [ ] `error` fires only for uncaught client errors; each block's named failures stay with the block.
- [ ] Every dashboard metric names its definition: classic or rolling, calendar day or window, revenue basis.
- [ ] Retention, payback and stability gates come from soft-launch cohorts.
- [ ] Rewards, timers, event definitions, product slots and kill switches are server-controlled; prices, secrets and balance decisions are not.
- [ ] Compiled defaults exist, a rollback is tested, and each flag-gated feature appears in the review notes.
- [ ] Each experiment has a hypothesis, a primary metric, guardrails, a planned end and a mismatch check, and no arm pressures minors or targets vulnerability signals.
- [ ] Each event or drop passed its gate: owner and reviewer named; reward value approved against sinks; timers as absolute `ends_at`; copy keys in every shipped locale; odds disclosed where random; dashboards live; kill switch tested; QA run with the test clock; support text and incident owner ready.
- [ ] The test clock works only for allowlisted tester accounts, and those accounts are excluded from metrics.
- [ ] The incident runbook covers stop, scope from the ledger, compensate, announce and postmortem.
- [ ] The server validates inputs, rate-limits claim and purchase endpoints, verifies rewarded ads and purchases, and logs integrity verdicts on high-value flows.
- [ ] Crash and ANR rates are alarmed below Google's thresholds per version and device model, and releases use staged rollout.
- [ ] Offline behavior is tested: money actions queue as intents, events queue on the device, timers read `server_now`.
- [ ] The minimum-version gate works on both platforms.
- [ ] Copy uses plural categories, and the control-size, contrast and text-scaling floor is met.
- [ ] Privacy labels, consent, ATT, children handling, retention windows and deletion were reviewed before submission.
